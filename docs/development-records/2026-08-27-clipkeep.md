# ClipKeep 剪贴板历史工具 —— 开发记录

- 日期：2026-08-27
- 环境：macOS 15.7.7 (24G720) / arm64 / Swift 6.1.2 (仅 Command Line Tools，无完整 Xcode)
- 产物：`ClipKeep/build/ClipKeep.app`

## 1. 任务概述与技术方案

### 需求

菜单栏常驻的剪贴板历史工具：复制后无感记录，设置快捷键后可快速调出历史记录，方便再次复制。

### 范围

**范围内**：后台监听复制并自动去重记录（文本 + 图片）、全局快捷键唤出搜索面板、方向键选择与回车回填、本地 SQLite 持久化、容量与时间双上限清理、收藏置顶、密码类内容自动跳过、菜单栏图标与偏好设置。

**非目标**（明确不做）：iCloud/跨设备同步、富文本样式保真、自动粘贴到前台 app（需辅助功能授权，违背零授权目标）、文件路径记录、公证分发。

### 需求前提修正

用户原始描述为"安装以后只需要授权以后，就可以在复制以后无感记录"。**实测证明核心功能无需任何授权**，据此调整设计目标为"零授权"：

| 能力 | 实测结果 | 授权需求 |
|---|---|---|
| 读剪贴板 `NSPasteboard.string()` | `readOK=true`，同时 `AXIsProcessTrusted=false` | 不需要 |
| 全局快捷键 `RegisterEventHotKey` | `status=0 (noErr)` | 不需要 |
| 菜单栏 `NSStatusItem` | `statusItemCreated=true` | 不需要 |
| SQLite + WAL | `open=0 wal=0 threadsafe=2` | 不需要 |
| `.app` + ad-hoc 签名 | `Signature=adhoc`，可运行 | 不需要 |

对照方案：用 `CGEventTap` 监听 `Cmd+C` 按键需要「输入监听」权限（等同全局键盘记录），既有隐私风险又需用户手动配置系统设置。**已否决**。

### 架构

```
ClipKeep.app
├─ ClipKeepMain/AppDelegate ... LSUIElement=true，无 Dock 图标
├─ ClipboardMonitor .......... Timer 0.3s 轮询 changeCount + 竞态重试读取
├─ ClipStore ................. SQLite(WAL)，串行队列，UNIQUE(content_hash) 原子去重
├─ ImageCodec ................ TIFF→PNG 重编码 + 收敛式降分辨率 + 缩略图
├─ PrivacyFilter ............. 三层密码/敏感内容过滤
├─ HotKeyManager ............. Carbon RegisterEventHotKey，可改键
├─ HistoryPanelController .... NSPanel(.nonactivatingPanel)，不抢前台焦点
├─ HistoryView ............... SwiftUI 列表 + NSTextField 承载键盘导航
└─ Settings/SettingsStore .... JSON 偏好，权限 0600，数值夹取
```

### 关键技术选型

- **轮询而非事件监听**：macOS 不提供剪贴板变更通知 API。0.3s 轮询，`changeCount` 未变时不读内容，空闲开销为一次整数比较。
- **`swiftc` 直编 + 手工 bundle**：本机 `xcodebuild` 不可用（仅 CLT）。实测该路径可产出可运行的签名 `.app`，无需安装完整 Xcode。
- **SQLite 而非 JSON/UserDefaults**：需要唯一约束做原子去重、模糊搜索、有界清理。JSON 全量读写在数千条时性能不可接受。
- **`NSPanel(.nonactivatingPanel)`**：面板不激活自身、不抢前台焦点，用户取回内容后可直接在原位置 `Cmd+V`。这是"不打断工作流"的核心。

## 2. 交互决策过程

用户初选唤出快捷键为 `Cmd+C`。实测 `RegisterEventHotKey(Cmd+C)` 返回 `status=0` 注册成功，但 **Carbon 热键会拦截按键、不向前台 app 传递**，即注册后 `Cmd+C` 不再执行复制，工具会废掉自己赖以工作的输入源。

已向用户说明该冲突，并实测验证了替代方案「双击 `Cmd+C`」可行（纯轮询检测，不注册热键、不拦截按键）：

```
single cc=433 v=same-text
>>> DOUBLE-COPY DETECTED gap=0.358s content=same-text
single cc=435 v=other gap=1.440       ← 间隔 1.4s 正确判为两次独立复制
single cc=436 v=other gap=1.559
```

用户随后依次选择 `Option+V`（实测可注册，但会占用 `√` 字符输入，已告知）、最终确定 **`Cmd+Shift+V`**。已实现为可在配置文件中修改。

## 3. 实施步骤与验证结果

### 阶段一：可行性实证（编码前）

在编写任何产品代码前，先用一次性探针程序验证全部平台假设，避免方案建立在错误前提上。验证项见上文"需求前提修正"表格，全部通过。

### 阶段二：数据层

`ClipStore` 实现后编写 18 项断言测试（`/tmp/storetest.swift`），覆盖插入、去重、搜索、LIKE 转义、收藏置顶、双上限清理、图片独立计数、BLOB 懒加载、200 并发写入。

**首轮发现缺陷**：`T8 after=5`，预期 6。原因是收藏项占用了保留配额 —— 若用户收藏满 200 条，全部普通历史会被立即清空。

修复：清理子查询改为仅在非收藏行中取 `LIMIT N`。

最终结果（18/18 通过）：

```
T1 firstInsert=true          T2 dupIsUpdate=true count=1
T3 count=2                   T4 topIsHello=true
T5 search(wor)=1             T5b searchNoMatch=0
T6 searchPercent=1           T6b searchUnderscore=0      ← LIKE 通配符转义生效
T7 favTop=true               T8 before=23 removed=17 after=6   ← 修复后正确
T9 removedOld=true ancientGone=true                      T10 favSurvived=true
T11 imagesKept=3             T12 imgPreview=[图片] 800×600
T13 recentNoBlob=true fullHasBlob=true                   T13b thumbInRecent=true
T14 concurrentErrs=0 distinctRows=20                     ← 200 并发零错误
T15 remaining=1 allFav=true
```

### 阶段三：图片编解码

实测剪贴板图片为**未压缩 TIFF**：一张 2880×1800 Retina 截图为 **158MB**。直接落库会让几张截图吃掉数 GB，必须重编码。

```
rawTIFFbytes=165906726 (158MB) → reencodedPNGbytes=1696389 (1656KB)  压缩 97 倍
thumbPNGbytes=7107
```

**发现缺陷（P1）**：初版仅缩放一次即放弃。用不可压缩噪点图（2600×2600）强制触发该分支后：

```
png=13887KB px=2048x2048    ← 缩放后仍 13.8MB，超 5MB 上限 2.7 倍
thumb=140136B               ← 缩略图 140KB，远超预期 7KB
```

修复三处：
1. 改为**收敛式循环**降分辨率（长边逐次减半，下限 256px，最多 5 次），仍超限则拒绝记录而非放任入库。
2. 缩略图同样加入循环收敛，上限 24KB。
3. 阈值从 5MB 下调至 **2MB**（正常 Retina 截图重编码后仅 93KB，该阈值只用于拦截病态图像）。

修复后：

```
T1 病态噪点图: png=715KB px=512x512 underImageCap=true thumb=6818B underThumbCap=true
T2 正常Retina截图: px=2880x1800 noScale=true png=93KB thumb=1338B
T3-T6 小图/极窄图/1x1/垃圾输入/hash稳定性 全部通过
```

另修正测试辅助函数缺陷：`NSImage.lockFocus()` 在 Retina 上按 backing scale 隐式 2 倍放大，导致早期测试的尺寸断言失真（生产代码 `ImageCodec.resized` 已显式构造 `NSBitmapImageRep` 并设置像素尺寸，不受此影响）。

## 4. 问题、根因与解决

| # | 问题 | 根因 | 解决 | 严重度 |
|---|---|---|---|---|
| 1 | 剪贴板读取偶发返回 nil（实测 `read#3 ok=false`） | 写入方递增 `changeCount` 早于数据写入完成 | 最多重试 5×15ms；期间 `changeCount` 再变则放弃本轮（新内容触发下一轮）。实测缓解后 6/6 成功 | 高（丢记录） |
| 2 | 收藏项占用保留配额，收藏满额会清空全部普通历史 | 清理子查询在全部行中取 `LIMIT N` | 子查询限定 `is_favorite = 0` | 高（数据丢失） |
| 3 | 病态图像缩放后仍 13.8MB 入库，缩略图 140KB | 只缩放一次即放弃 | 收敛式循环 + 下限拒绝 + 阈值降至 2MB + 缩略图独立收敛 | 中（磁盘失控） |
| 4 | `Cmd+C` 作为热键会废掉复制功能 | Carbon 热键拦截按键不向前台传递 | 向用户说明并改用 `Cmd+Shift+V` | 高（功能自毁） |
| 5 | 回填剪贴板会被自己的监听重复记录 | 回填导致 `changeCount` 变化 | `willWriteToPasteboard()` 预登记下一个 `changeCount` 并在 tick 中跳过 | 中（历史污染） |
| 6 | LIKE 搜索中用户输入的 `%`/`_` 被当作通配符 | 未转义 | `ESCAPE '\'` + 转义 `\ % _`。实测搜 `%` 返回 1 条而非全部 | 低 |
| 7 | 数据库损坏导致无法启动 | 未处理损坏场景 | 备份坏档（含 `-wal`/`-shm`）后重建并告知用户备份路径 | 中（可用性） |
| 8 | Swift 6 actor 隔离与 Sendable 告警 | Timer 回调 nonisolated | `@MainActor` 标注 + `Task { @MainActor }` + `@unchecked Sendable` 并注明不变式 | 低 |

## 5. 安全处理

密码泄露被列为最高优先级约束（明文历史库若记录密码，等同摊开密码库）。三层独立判据，任一命中即跳过：

1. `org.nspasteboard.ConcealedType` / `AutoGeneratedType` 标记（密码管理器通用约定）
2. `org.nspasteboard.TransientType` 临时内容标记
3. 来源 bundle id 黑名单（1Password、Bitwarden、KeePassXC、钥匙串访问、Enpass、Dashlane、LastPass、Keeper、mSecure 等 11 项前缀，大小写不敏感，支持用户追加）

数据库权限 0600，目录 0700。**已用 `strings` 对库文件做二进制扫描确认密码无残留**。

明文存储本身是剪贴板管理器的固有属性，未加密，已在 README 中明确声明而非淡化。

其他：SQL 全部使用参数绑定（`sqlite3_bind_*`），LIKE 通配符转义，无硬编码凭据，无网络调用，配置数值夹取到安全区间防止手工编辑导致资源失控。

`frontmostBundleID()` 为启发式判断（用户复制后立刻切换 app 可能取到错误来源），已在代码注释中说明；因来源仅用于黑名单辅助与展示，密码过滤以 ConcealedType 标记为主判据，故该误差可接受。

## 7. SQL 与数据迁移

**无既有数据迁移，无破坏性语句，无回滚脚本需求** —— 本次为全新数据库，所有 DDL 均为 `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS`，幂等且可重复执行。

初始 DDL（执行顺序即代码中顺序，位于 `ClipStore.migrate()`）：

```sql
-- 1. 主表
CREATE TABLE IF NOT EXISTS clips (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    kind           TEXT    NOT NULL,              -- 'text' | 'image'
    content        TEXT    NOT NULL DEFAULT '',
    preview        TEXT    NOT NULL DEFAULT '',
    content_hash   TEXT    NOT NULL UNIQUE,       -- 去重键，SHA-256
    source_app     TEXT,
    is_favorite    INTEGER NOT NULL DEFAULT 0,
    created_at     REAL    NOT NULL,
    updated_at     REAL    NOT NULL,
    image_data     BLOB,
    thumbnail_data BLOB,
    pixel_width    INTEGER,
    pixel_height   INTEGER
);

-- 2. 列表倒序索引
CREATE INDEX IF NOT EXISTS idx_clips_updated ON clips(updated_at DESC);

-- 3. 按类型倒序索引（保留策略按类型分别计数）
CREATE INDEX IF NOT EXISTS idx_clips_kind_updated ON clips(kind, updated_at DESC);
```

PRAGMA（每次打开连接时执行）：`journal_mode=WAL`、`synchronous=NORMAL`、`busy_timeout=3000`。

运行时 DML 要点：

```sql
-- 幂等写入：单条语句原子完成"新增或刷新时间戳"，不存在 check-then-insert 竞态
INSERT INTO clips (...) VALUES (...)
ON CONFLICT(content_hash) DO UPDATE SET
    updated_at = excluded.updated_at,
    source_app = excluded.source_app;

-- 保留策略：超龄清理（收藏豁免）
DELETE FROM clips WHERE is_favorite = 0 AND updated_at < :cutoff;

-- 保留策略：超量清理（收藏豁免且不占配额 —— 见问题 #2）
DELETE FROM clips
WHERE is_favorite = 0 AND kind = :kind
  AND id NOT IN (
      SELECT id FROM clips
      WHERE kind = :kind AND is_favorite = 0
      ORDER BY updated_at DESC LIMIT :keep
  );
```

安全说明：`DELETE` 均带 `is_favorite = 0` 保护，收藏记录只能由用户手动单条删除。`clearAll` 默认 `keepFavorites: true`，且在 UI 层有二次确认弹窗。所有用户输入经 `sqlite3_bind_*` 参数绑定，无字符串拼接。

## 8. 未验证项与残留风险

**未能验证**（受环境限制，已如实记录）：

- **面板交互未经真人操作验证**。唤出面板需真实按键，而模拟按键需辅助功能授权 —— 该授权正是本设计刻意规避的对象，故无法自动化。已交付用户手动验证 `Cmd+Shift+V` → ↑↓ → Enter → Esc 流程。代码路径（面板创建、定位、键盘处理、回填）已通过编译期检查，但运行时行为待确认。
- **开机自启未端到端验证**。`SMAppService.mainApp.register()` 需 app 位于 `/Applications` 且用户在系统设置中批准，当前 app 运行于构建目录。API 可用性已探针确认（返回 `status=3 notFound`，符合未注册状态的预期）。
- **Intel 机器未验证**。`build.sh` 目标为 `arm64-apple-macosx13.0`，x86_64 需修改 target 后重新验证。
- **macOS 13/14 未验证**。声明 `LSMinimumSystemVersion=13.0` 且已避开 macOS 14+ API（`onChange` 双参数形式），但仅在 15.7.7 上实际运行过。

**残留风险**：

| 风险 | 影响 | 缓解 |
|---|---|---|
| 轮询间隔 0.3s，快于该间隔的连续复制会漏记 | 丢记录。实测 20 次×0.1s 仅捕获 9 次 | macOS 无剪贴板通知 API，轮询是唯一途径。已在 README「已知限制」中声明 |
| 历史库明文存储 | 磁盘取证可读出剪贴板内容 | 权限 0600；README 明确声明未加密；密码类内容已过滤 |
| 密码管理器不遵循 ConcealedType 约定且不在黑名单内 | 该工具的密码可能入库 | 提供 `blockedSourcePrefixes` 供用户追加，README 给出查询 bundle id 的命令 |
| ad-hoc 签名，未公证 | 首次打开被 Gatekeeper 拦截 | README 给出右键打开与 `xattr` 两种方式 |
| `frontmostBundleID()` 启发式可能误判来源 | 来源标签显示错误；极端情况下黑名单漏判 | 密码过滤以 ConcealedType 为主判据，不单依赖来源 |

**后续工作**（未实现，非本次范围）：偏好设置图形界面（当前改配置需编辑 JSON 并重启）、快捷键可视化录制、富文本与文件路径支持、历史库加密选项、Intel/Universal 构建。

## 9. 回滚

本工具为独立新增 app，不修改系统配置、不触碰其他应用数据，回滚即卸载：

```bash
pkill -f ClipKeep
rm -rf /Applications/ClipKeep.app
rm -rf ~/Library/Application\ Support/ClipKeep    # 含全部历史记录，不可恢复
```

若曾开启开机自启，需在菜单栏关闭或在「系统设置 → 通用 → 登录项」中移除。

## 11. 追加：DMG 打包（同日）

### 需求与方案

将 app 打包为可分发的 DMG 安装包。全部使用 macOS 自带工具（`hdiutil` / `osascript` / `PlistBuddy`），无第三方依赖（不引入 create-dmg 等 npm/brew 包，避免供应链风险）。

脚本：`package-dmg.sh`。流程为：校验 app 签名 → 组装内容（app + Applications 符号链接 + 说明文件）→ 生成 UDRW 可写镜像 → 挂载并用 Finder 设置图标布局 → 清理系统元数据 → 转换为 ULFO（lzfse）压缩镜像 → ad-hoc 签名 → `hdiutil verify` 校验 → 输出 SHA-256。

选择 ULFO 而非默认 UDZO：lzfse 压缩率更高。最终产物 **140KB**。

### 实施中的问题

| # | 问题 | 根因 | 解决 |
|---|---|---|---|
| 9 | Finder 布局设置静默失败，DMG 打开后为默认列表视图 | 挂载时用了 `-nobrowse`，Finder 看不到该卷，AppleScript 无法按 `disk "名称"` 寻址 | 去掉 `-nobrowse`，改为解析 `hdiutil attach` 输出获取实际挂载点与卷名（同名卷已存在时系统会追加后缀，不能假定路径） |
| 10 | 挂载产生的 `.fseventsd` 进入最终镜像 | 系统在挂载卷上自动生成元数据目录 | 卸载前删除 `.fseventsd` / `.Trashes` / `.TemporaryItems` / `.Spotlight-V100` |

布局设置失败不阻断打包（`LAYOUT_OK` 标记 + 提示），因为它只影响观感，拖拽安装本身不依赖 `.DS_Store`；无 GUI 会话（如 CI）下必然失败，不应因此让打包失败。

**全新安装端到端模拟**（先清除 `/Applications/ClipKeep.app` 与 Application Support 目录）：

| 步骤 | 结果 |
|---|---|
| 给 DMG 打 quarantine 标记模拟网络下载 | 成功 |
| 挂载并 `cp -R`（等价 Finder 拖拽）到 `/Applications` | 成功，签名仍有效 |

至此**安装链路完整验证**：DMG → 拖拽 → 解除拦截 → 启动 → 自动记录正常。

### 开机自启（仍未验证）

app 现已位于 `/Applications`（满足 `SMAppService` 的位置要求），但 `SMAppService.mainApp.register()` 必须由 app 自身进程调用，无法从外部脚本触发。独立探针返回 `status=3 notFound`，符合"非 bundle 内调用"的预期。

**该项仍需用户手动点击菜单栏「开机自动启动」验证**，首次注册后需在「系统设置 → 通用 → 登录项」批准（代码已在 `status == .requiresApproval` 时提示用户）。
